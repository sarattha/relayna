Performance

Methodology

Fixtures use fixed identifiers and timestamps. ASCII-heavy and Unicode/numeric profiles are calibrated so the current outbound bytes are exactly 1,024, 16,384, 131,072, and 1,048,576 bytes for both TaskEnvelope and two-task BatchTaskEnvelope messages. “Actual bytes” reports each candidate’s emitted or consumed bytes; alias-compatible payloads are slightly larger because documentId replaces task_id.

Outbound measurements include model_dump(mode="json", exclude_none=True) where applicable, JSON encoding, and AMQP-ready bytes. The implemented private production codec and orjson receive the current prepared mapping; raw engine speed is not substituted for model-aware preparation. Inbound canonical measurements start with current wire bytes and end with a validated envelope. Alias measurements additionally preserve Relayna’s recursive documentId normalization. The direct Pydantic alias case includes a failed direct validation and explicit Pydantic Core normalization fallback.

Every candidate is checked for validated semantic equivalence before timing. Each operation receives a warm-up call. Values are medians of repeated perf_counter_ns samples; the displayed P25–P75 interval is the useful dispersion measure. Garbage collection is disabled only within timed loops, and case order rotates/reverses by repeat. MiB/s uses 1,048,576 bytes. Relative speedup is current median divided by candidate median. orjson was installed and measured.

Packaging and reproducibility

The chosen production codec uses Pydantic Core 2.41.5, already installed through Relayna’s Pydantic dependency. It adds no package or native-wheel perimeter. orjson is pinned only in Relayna’s optional [benchmark] extra as orjson==3.11.9; it is not in production [project].dependencies. The canonical command is:

uv run --extra benchmark python -m benchmarks run json-engine-evaluation

Wheel filenames below were verified against the PyPI release metadata for Pydantic Core 2.41.5 and orjson 3.11.9. macOS universal2 artifacts cover x86_64 as well as ARM64; dedicated ARM64 wheels are also published. Native wheels reduce contributor setup risk, but a production dependency would still add a Rust-backed native extension, platform artifact tracking, and supply-chain surface.

Implemented production strategy

  1. Change only Relayna-owned AMQP transport bodies; keep storage, canonical hashing, deduplication, and persisted serializers unchanged.
  2. Use private relayna._transport_json helpers backed by Pydantic Core for compact outbound AMQP bytes and strict inbound parsing.
  3. Continue existing alias normalization and Pydantic envelope validation after parsing, keeping malformed syntax in the parse stage and valid invalid envelopes in the validation stage.
  4. Do not add orjson to production. Keep it benchmark-only because its extra outbound gain does not justify its native dependency and narrower numeric/domain behavior.

Next benchmark

Before broad rollout, run a deterministic consumer-classification replay benchmark. Matrix: codec (released v1.4.29 stdlib, implemented Pydantic Core); envelope (task, two-task batch); size (1 KB, 16 KB, 128 KB); traffic mix (100/0, 95/5, and 80/20 canonical/alias); validity (valid, malformed JSON, invalid UTF-8, valid invalid envelope); and configured alias on/off. Measure total CPU latency, allocations, malformed/invalid counts, and rejection-stage parity. This tests realistic traffic mixes and provides canary alert thresholds before deployment, still without network latency.

Limitations

  • Local CPU observations are not cross-machine guarantees; use relative comparisons and rerun on production-representative Linux x86_64 and aarch64 hosts.
  • No RabbitMQ, Redis, scheduling, async dispatch, or network work is included.
  • Compatibility probes cover known Relayna boundaries but do not replace a captured production-corpus replay.
